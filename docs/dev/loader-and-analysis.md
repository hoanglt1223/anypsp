# Loader and analysis

How AnyPSP turns a decrypted `EBOOT.BIN` and the game's PRX modules into the function list the code generator translates. The code lives in `recomp/loader/`, `recomp/analysis/` and `recomp/tools/anypsp_analyze.cpp`. The runtime side of trace feedback lives in `recomp/src/runtime.cpp` and `runtime/host/main_headless.cpp`.

## Inputs: decrypted executables only

AnyPSP reads plain ELF and PRX files. It unpacks a PBP's `DATA.PSP`, and it refuses `~PSP`/`~SCE` (encrypted or compressed) and gzip input with an explanation. AnyPSP ships no keys and contains no decrypter. To produce the input, decrypt `PSP_GAME/SYSDIR/EBOOT.BIN` and the `.PRX` files of your own dump with an existing tool. Two examples:

- PPSSPP's developer setting that dumps the decrypted EBOOT when a game boots.
- PRXdecrypter on a PSP running custom firmware.

PGD-encrypted data files are refused at run time for the same reason.

## Pipeline

```
anypsp-analyze --out <dir> [--layout layout.txt] [--feedback feedback.txt]... EBOOT.BIN [MODULE.PRX ...]
psp_recomp EBOOT.BIN --auto <generated dir> --seeds <dir>/0_EBOOT.BIN_seeds.csv
cmake -S . -B out/runners/<name> -DANYPSP_RUNNER_NAME=<name> -DANYPSP_RUNNER_GENERATED=<generated dir>
out/runners/<name>/Release/anypsp-run-<name>.exe EBOOT.BIN --frames 600 --feedback feedback.txt
```

`python tests/feedback-pass.py <module>` runs these steps in a loop. Each pass feeds the previous run's feedback back into the analysis.

1. **Load** (`loader/elf_prx`, `loader/relocs`). This step:
   - copies every `PT_LOAD` segment;
   - applies relocations in all three PSP formats: `SHT_PSPREL` sections, `0x700000A0` program headers, and packed `0x700000A1` program headers (the packed format follows PPSSPP's `LoadRelocations2`);
   - finds the module info by section name, or by the first program header's `p_paddr` when the file has no section headers;
   - reads function and variable imports and exports.

   A PRX cut off before its relocation tables loads unrelocated, as on the PSP, and the unreadable tables are reported in the module's `problems`.
2. **Layout.** The first module goes to `0x08804000` (an `ET_EXEC` image goes to its own address). The other modules are stacked down from `0x0A000000`, aligned to 256 bytes. `--layout` overrides any module's base; each line is `<base> <path>`, the same format as the `layout.txt` that `anypsp-analyze` writes.
3. **Imports** (`loader/nid_db`, `data/nids.toml`). Each import resolves in this order:
   - to another loaded module's export (`game_module`);
   - else to an HLE name from the NID database (`hle`);
   - else it is listed as `unknown` in `report.json` and `imports.csv`.

   `data/nids.toml` is generated by `tools/gen-nids.py` from PPSSPP's HLE tables and PSPSDK's stubs, with both commits recorded in its header. Regenerate it with:

   ```
   python tools/gen-nids.py --ppsspp ../../refs/ppsspp --pspsdk ../../refs/pspsdk --out data/nids.toml
   ```
4. **Function discovery** (`analysis/functions`). It starts from the base analysis (entry point, `jal` targets, code pointers materialised by `lui`/`addiu`, relocated pointers, prologues after a return). It then adds, repeating until no new entry appears:
   - exports and `module_start`/`module_stop`;
   - runtime feedback addresses;
   - jump-table targets;
   - code addresses passed to the APIs that take one: thread entries (`sceKernelCreateThread`), callbacks, alarms, vtimers, interrupt and thread-event handlers;
   - targets of tail-call `j`;
   - code after a function's final jump or `eret` (unreferenced functions, padding skipped);
   - for `ET_EXEC` images, code addresses stored in data sections.
5. **CFG** (`analysis/cfg`, `analysis/jumptables`):
   - A block that ends in a branch includes its delay slot.
   - A branch-likely is marked, because its delay slot runs only on the taken edge.
   - A branch target that is another branch's delay slot starts a block of its own.
   - `jr` through a register is resolved as a jump table when the code before it computes `table + index * 4`. The entry count comes from an `sltiu` bound check, or, without one, from reading entries until a non-code word.

## Outputs of `anypsp-analyze`

| File | Contents |
|---|---|
| `report.json` | Per module: base, relocation counts and format, problems, imports (`hle`/`game_module`/`unknown` with the unknown list), function count by seed source, jump tables, delay-slot findings, code pointers passed to system calls, feedback use, and symbol coverage (`symbols.missing`) when the file has a symbol table |
| `<n>_<module>_seeds.csv` | `name,address,source` for every function entry; input for `psp_recomp --auto --seeds` |
| `imports.csv` | Every import with its resolution |
| `layout.txt` | The load addresses used (`--layout` input) |

## Trace feedback

The runtime appends each code address it reaches without translated code, once, to a feedback file: `0x08804ABC missing_code` lines, `#` comments allowed. This covers dispatch misses, entries into a translated unit at a PC it never translated, and jumps the interpreter fallback takes to untranslated addresses. All of these then run in the interpreter rather than halting. Set the file with `PSPRECOMP_FEEDBACK_FILE` or `set_runtime_feedback_file`; the headless runner takes it as `--feedback <file>`. `anypsp-analyze --feedback` turns the addresses back into function seeds.

## Headless host

`anypsp_host` (CMake) is the psp-web-recomp HLE kernel with the software GE. It has no GL backend: the GE front end reaches a GPU backend only through `GeRenderer`, which the Vulkan backend will implement in phase 05. A runner (`anypsp-run-<name>`) links one game's generated code, opens no window and plays no audio. It runs with a 64 MiB stack, because translated calls nest native frames. `-DANYPSP_RUNNER_OPT=d|1|2` sets the optimisation level of the generated code; `d` builds fastest.
